# mattpocock/skills 项目笔记

github仓库：https://github.com/mattpocock/skills

## 一、项目概述

**作者**：Matt Pocock（TypeScript 教育者，Total TypeScript 创始人） 

**定位**：一套给 Claude Code 及其他 AI 编程 agent 用的"技能包"，解决 AI 辅助开发中最常见的失败模式。

**安装**：`npx skills@latest add mattpocock/skills`，每个项目运行一次 `/setup-matt-pocock-skills` 完成配置。

### 核心设计哲学

> "小、可组合、可适配的 skills，基于工程基础——而不是把开发者排除在外的自动化流水线。"

针对四大失败模式：

| 失败模式 | 解决方案 |
|---|---|
| Agent 与开发者方向不一致 | `/grill-me` `/grill-with-docs` 先对齐再动手 |
| 输出冗余啰嗦 | `CONTEXT.md` 建立共享领域语言，减少解释 |
| 代码不可靠 | `/tdd` `/diagnose` 建立反馈循环 |
| 架构持续腐化 | `/improve-codebase-architecture` `/to-prd` `/zoom-out` 日常设计投入 |

## 二、工程类 Skills（Engineering）

### `/diagnose` — 结构化调试

**触发**：说 "diagnose this" / "debug this" / 报告 bug / 性能回退

**核心思想**：调试的关键不是分析代码，而是先建立一个快速、确定性、可自动化运行的"反馈循环"。有了循环，bug 就解决了 90%。

**六阶段流程**：

```
Phase 1: 建反馈循环（最重要！）
  → 失败测试 / curl脚本 / CLI调用 / Playwright / 回放trace
  → 抛出harness / 属性测试 / git bisect / HITL bash脚本

Phase 2: 复现
  → 确认是用户描述的那个 bug，而不是旁边别的问题

Phase 3: 假设
  → 生成 3-5 个有排序的可证伪假设
  → 给用户看排序列表（便宜的检查点，节省大量时间）

Phase 4: 插桩
  → 每个探针对应 Phase 3 的一个预测，一次只改一个变量
  → 所有 debug log 加唯一前缀 [DEBUG-xxxx]，清理时 grep 一下就行

Phase 5: 修复 + 回归测试
  → 先写回归测试，再修复
  → 只在有"正确接缝"时才写测试

Phase 6: 清理 + 事后分析
  → 移除所有 [DEBUG-...] 插桩
  → 在 commit/PR 里说明是哪个假设最终正确
  → 问：什么能预防这个 bug？ → 交棒给 /improve-codebase-architecture
```

### `/tdd` — 测试驱动开发

**触发**：想用 TDD 写功能/修 bug，提到 "red-green-refactor"，要求先写测试

**核心原则**：测试验证行为，不验证实现。代码可以完全重写，测试不应该跟着坏。

**关键反模式：水平切片（严禁！）**

```
错误做法（水平切片）：
  RED:   test1, test2, test3, test4, test5  ← 一次写完所有测试
  GREEN: impl1, impl2, impl3, impl4, impl5  ← 再一次写完所有实现

正确做法（垂直切片/tracer bullet）：
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
```

水平切片的问题：测试的是想象中的行为，而不是真实行为；容易测数据结构形状而不是用户可见行为。

**工作流**：
1. 规划：与用户确认接口变更和要测哪些行为，设计可测试性接口
2. Tracer Bullet：写一个测试，验证一件事，先红后绿
3. 增量循环：每次一个测试 → 最少代码通过 → 重复
4. 重构：所有测试绿了才重构，重构中途不能有红测试

---

### `/improve-codebase-architecture` — 架构改进

**触发**：想改进架构、找重构机会、消除耦合、提升可测试性

**专用术语**（必须使用这套词汇，不能说 "service/component/boundary"）：

| 术语 | 含义 |
|---|---|
| Module | 有接口和实现的任何东西 |
| Interface | 调用方需要知道的一切（类型、不变量、错误模式） |
| Depth（深度） | 接口小、实现丰富 = 深模块；接口≈实现 = 浅模块 |
| Seam（接缝） | 接口所在的位置；可以不改实现而改行为的地方 |
| Leverage（杠杆） | 调用方从深度获得的收益 |
| Locality（局部性） | 维护方从深度获得的收益：变更、bug、知识集中在一处 |

**"删除测试"**：想象删掉这个模块。如果复杂性消失了 → 它是透传层。如果复杂性重新出现在 N 个调用方 → 它在赚取自己的位置。

**流程**：探索代码 → 列出"深化机会"候选 → 与用户讨论 → grilling 对话 → 命名新模块时同步更新 `CONTEXT.md`

---

### `/grill-with-docs` — 结合文档的设计审查

**触发**：想压力测试一个方案，且项目有 `CONTEXT.md` / ADR

**比 `/grill-me` 多做的事**：
- 用 `CONTEXT.md` 词汇挑战你用词（"你说的 cancellation 是 X 还是 Y？你的词汇表定义了 X"）
- 交叉核对代码（"你说支持部分取消，但代码里取消的是整个 Order"）
- 决策结晶时内联更新 `CONTEXT.md` 和 ADR，不等到最后才批量写

**ADR 的创建标准**（三条全满足才写）：
1. 难以逆转——改变代价大
2. 不看上下文会困惑——未来读者会问"为什么这样"
3. 真实权衡——有过真实备选方案

---

### `/grill-me` — 设计压力测试

**触发**：说 "grill me"，想压力测试方案

逐一追问每个决策树分支，每个问题给出推荐答案，等你回答后再问下一个。如果问题能通过探索代码回答，就去探索代码而不是问你。

---

### `/to-prd` — 生成 PRD

**触发**：聊完需求后，想生成 PRD 文档

**流程**：
1. 探索代码库了解当前状态
2. 梳理需要构建/修改的模块，找"深模块"机会
3. 用模板生成 PRD，写入 `.scratch/<feature>/PRD.md`，打上 `ready-for-agent` 标签

**PRD 模板包含**：Problem Statement / Solution / User Stories（尽量详尽）/ Implementation Decisions / Testing Decisions / Out of Scope / Further Notes

---

### `/to-issues` — 拆解成 Issue

**触发**：把计划/PRD 拆成独立可执行的 issue

**核心规则：垂直切片（tracer bullet）**，每个 issue 是一个从头切到尾的薄切片（schema→API→UI→测试），可以独立演示，而不是"先做所有后端，再做所有前端"的水平切片。

**Issue 类型**：
- **HITL**（Human in the Loop）：需要人工决策（架构决定、设计评审）
- **AFK**（Away From Keyboard）：完全规格化，agent 可独立完成并合并

**流程**：收集上下文 → 起草切片列表 → 跟用户确认粒度和依赖关系 → 按依赖顺序发布到 issue tracker

---

### `/triage` — Issue 分流

**触发**：创建 issue、处理 bug 报告、准备给 AFK agent 执行的任务

**状态机**：

```
unlabeled → needs-triage → needs-info ← (reporter 回复后)
                         → ready-for-agent  (AFK agent 可执行)
                         → ready-for-human  (需要人工)
                         → wontfix
```

**每个 issue 的处理流程**：
1. 读全文（body + comments + labels）
2. 推荐分类 + 给出理由，等维护者决定
3. Bug 专项：尝试复现，追踪代码路径
4. 如需要，跑 `/grill-with-docs` 补充细节
5. 发布到 issue tracker 的每条评论都要加免责声明：`> *This was generated by AI during triage.*`

---

### `/prototype` — 快速原型

**触发**：说 "prototype this" / "let me play with it" / "try a few designs"

**先判断问题类型，选择分支**：

| 问题 | 分支 |
|---|---|
| "这个逻辑/状态模型对不对？" | LOGIC 分支：构建可交互的终端 app，推动状态机走各种 case |
| "这个应该长什么样？" | UI 分支：生成几个完全不同的 UI 方案，通过 URL 参数切换 |

**原则**：
- 从第一天起就是"可丢弃代码"，要明确标注
- 一条命令就能运行
- 默认无持久化（状态在内存里）
- 不要打磨（无测试、无错误处理、无抽象）
- 每次操作后显示完整状态
- 用完就删，或者把决策折叠进正式代码

---

### `/zoom-out` — 缩放到更高层次

**触发**：不熟悉某段代码，需要了解更大的上下文

本质是：往上走一个抽象层级，用项目领域词汇，给出所有相关模块和调用者的地图。

## 三、生产力类 Skills（Productivity）

### `/handoff` — 对话交接文档

**触发**：上下文快满了，或者想让另一个 agent 接着做

生成一个交接文档，保存为临时文件（`mktemp -t handoff-XXXXXX.md`）。
- 不重复 PRD / ADR / issue / commit 里已有的内容，只引用路径
- 建议下一个 session 应该用哪些 skills
- 可以传参描述下一个 session 的重点

---

### `/caveman` — 极简模式

**触发**：说 "caveman mode" / "less tokens" / "be brief"

砍掉所有废话，保留所有技术内容，节省约 75% token。

**去掉**：冠词（a/an/the）、填充词（just/really/basically）、客套话（sure/certainly/happy to）、对冲语气。
**保留**：所有技术术语、代码块（原封不动）、错误信息（精确引用）。

**例子**：
- 原来："Sure! I'd be happy to help you with that. The issue you're experiencing is likely caused by..."
- Caveman："Bug in auth middleware. Token expiry check use `<` not `<=`. Fix:"

**安全例外**：安全警告、不可逆操作确认 → 暂时恢复正常语言，完成后继续 caveman 模式。

---

### `/write-a-skill` — 创建新 Skill

**触发**：想创建自己的自动化 skill

**Skill 文件结构**：
```
skill-name/
├── SKILL.md        # 主指令（必须）
├── REFERENCE.md    # 详细文档（可选）
├── EXAMPLES.md     # 用法示例（可选）
└── scripts/        # 工具脚本（可选）
```

**描述字段规范**（这是 agent 决定加载哪个 skill 的唯一依据）：
- 最多 1024 字符
- 第一句：做什么
- 第二句："Use when [具体触发条件]"
- 用第三人称

## 四、杂项 Skills（Misc）

### `/git-guardrails-claude-code` — Git 安全护栏

**触发**：一次性配置，防止 Claude Code 执行危险 git 操作

**拦截命令**：`git push`（含 `--force`）、`git reset --hard`、`git clean -f/fd`、`git branch -D`、`git checkout .` / `git restore .`

**工作原理**：在 `PreToolUse` hook 里拦截 Bash 工具调用，Claude 会看到"没有权限执行这些命令"的提示。

**作用域**：可选项目级（`.claude/settings.json`）或全局（`~/.claude/settings.json`）。

### `/migrate-to-shoehorn` — TypeScript 测试断言迁移

**适用场景**：TypeScript 项目，测试里有大量 `as` 类型断言

**解决的问题**：测试时只需要对象的部分字段，但 TypeScript 要求完整类型，导致大量 `as Request` 或 `as unknown as Request`。

**替换规则**：

| 原来 | 替换为 | 场景 |
|---|---|---|
| `obj as Type` | `fromPartial(obj)` | 传部分字段，类型仍合法 |
| `obj as unknown as Type` | `fromAny(obj)` | 故意传错误类型（错误测试） |
| 完整对象 | `fromExact(obj)` | 强制完整对象 |

**注意**：只用于测试代码，严禁用于生产代码。

## 七、支撑系统：Domain Docs

这套 skills 的很多功能依赖两类文档：

### `CONTEXT.md` — 领域词汇表
- 只放词汇定义，不放实现细节
- 不要把它当 spec 或 scratch pad
- 被 `/grill-with-docs`、`/tdd`、`/improve-codebase-architecture`、`/triage` 读取
- 由 `/grill-with-docs` 在对话中实时更新

### `docs/adr/` — 架构决策记录（ADR）
- 记录"为什么这样做"，不记录"做了什么"
- 只在满足三条时才写：难以逆转 + 没上下文会困惑 + 真实权衡
- 被所有工程类 skills 读取，避免重复踩坑

## 八、典型工作流组合

```
发现需求
  → /grill-me 或 /grill-with-docs    # 对齐，先搞清楚要做什么
  → /to-prd                           # 生成 PRD
  → /to-issues                        # 拆成 issue
  → /triage                           # 分配给 agent 或人工

开始实现
  → /zoom-out                         # 理解相关模块
  → /prototype                        # 验证设计（可选）
  → /tdd                              # 测试驱动开发

遇到 bug
  → /diagnose                         # 结构化调试

代码质量
  → /improve-codebase-architecture    # 周期性架构复查

上下文管理
  → /handoff                          # 上下文快满时交接
  → /caveman                          # 节省 token
```
